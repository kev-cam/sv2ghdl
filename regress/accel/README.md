# test/accel/bench -- a measurable `--accel` benchmark suite

Purpose: give `nvc --accel` designs that are **big enough to measure**, **correct**,
**scalable**, and **runnable on Verilator with the identical workload**, so the
generated code can be optimised against a real number instead of a guess.

Everything here is generated by `gen.py` from one source of truth, so the VHDL and
the SystemVerilog are the same design by construction. `run.sh` builds and verifies
every case in every mode and prints a table.

```
./run.sh              # verify all cases in all modes
./run.sh -t           # ...and collect `perf stat -e instructions`
./run.sh wide_n8w1024 # one case
./materialise.sh      # write the canonical size of each shape into designs/
```

## What each run compares

| mode | how |
|---|---|
| `interp` | `nvc -r` (no accel) -- the gold reference |
| `accel` | `NVC_ACCEL=1 NVC_ACCEL_JIT=1 NVC_ACCEL_FROM_VHDL=1`, **default admission gate** |
| `perinst` | as above plus `NVC_ACCEL_PER_INSTANCE=1 NVC_ACCEL_MIN_MODULES=1` |
| `vltr` | Verilator `--binary` on the matched `.sv` |

All four must print the same `Y=`. The testbench is structurally identical in both
languages: a 32-bit maximal LFSR (`x^32+x^22+x^2+x^1+1`, seed `ACE1BEEF`) drives
`d`, `rst` is held for 4 cycles, and a 32-bit rotate-xor checksum
`chk <= {chk[30:0],chk[31]} ^ q` accumulates every cycle after reset.
`Y` is `chk[30:0]` (31 bits, so it fits a VHDL `integer`).

`Y` matching across nvc-interp, nvc-accel and Verilator is *verified*, not assumed --
it is the first three columns of the table lining up with the fourth.

## Admission: no `NVC_ACCEL_MIN_MODULES` knob is used

`--accel` has two counting gates that key on nothing about the amount of work in a
design (`src/rt/model.c:5177` and `:5233`, both default 8): the subtree needs
**>= 8 `SCOPE_INSTANCE` nodes** *and* **>= 8 distinct `(entity, generics)`
variants**. Every design here is shaped to clear both naturally, by instantiating
one generic leaf N >= 8 times with **distinct generics** -- so `run.sh` never sets
`NVC_ACCEL_MIN_MODULES` in the `accel` column. (It is set in the `perinst` column
only, because per-instance chunks are single leaves by definition.)

Two consequences worth knowing before editing anything here:

* **`for ... generate` is declined by the translator.** `vhdl2vlog.c:1843` only
  accepts an elaborated `T_BLOCK` whose `T_HIER` ref is a `T_ARCH`; a generate
  scope is not, so it emits `/*?block k=60*/` and the whole subtree declines.
  That is why the structural repetition is emitted by `gen.py` rather than written
  as a generate loop. Measured: a 16-leaf chain written with `for..generate`
  declines at every size; the same chain written flat installs.
* **Component instantiation is declined too** (same site). Direct
  `entity work.X` only.

## The six shapes

| shape | what it stresses | scaling knobs |
|---|---|---|
| `wide` | WIDE datapath -- wide add/sub/xor/rotate/compare on `W`-bit buses. This is the shape that produces the wide intermediates and the bit-serial `wplace`. | `N` stages, `W` bits |
| `fsm` | NARROW/control -- chain of 16-state FSMs, 4-bit state, 4-bit interconnect, 16-way `case`. The contrast against `wide` is the diagnostic. | `N` stages |
| `deep` | DEEP combinational -- `D` chained **pure-comb** stages between two registers; delta settling and comb-cone stress. | `D` depth, `W` bits |
| `regf` | REGISTER-heavy -- `N` banks x `DEPTH` x 32b of explicit flops with a `case` write decoder and a synchronous read mux; `sm_clock` stress. | `N`, `DEPTH` |
| `many` | MANY chunks -- `K` clusters, each an 8-stage FSM chain. The top carries a deliberate `assert` so the top *declines* and the scan **descends**, installing one chunk per cluster. | `K` clusters, `M` stages |
| `act` | LOW activity -- enable-gated stages, 1-of-N hot per cycle. `-gALLON=1` makes every stage hot **with the identical netlist**, so `act_lo` vs `act_hi` isolates activity from structure. | `N`, `W`, `ALLON` |

`act`'s `mode` is a real input port, not a generic, precisely so yosys cannot
constant-fold the two variants into different netlists. `act_lo` and `act_hi` run
the same `.so`.

## Design rules every DUT here obeys

Breaking any one of these makes the chunk decline (often silently):

* direct `entity work.X` instantiation; no components, no `for..generate`
* `std_logic` / `std_logic_vector` ports only (no integer, record, real, bit)
* every flop is `if rising_edge(clk)` with a **reset-priority** synchronous reset,
  so nothing is ever `'U'` once the testbench releases reset
* no `assert` / `report` / procedure call / PSL anywhere inside a chunk
  (the one `assert` in `many_top` is deliberate and is the *reason* that design
  fragments)
* <= 4096 bits per boundary port and <= 4096 boundary pins. Wide designs keep the
  chunk boundary at 32 bits and expand internally, so `W` can scale freely.
* **no expressions in port maps** -- see the interpreter bug below.

## Known bugs found while building this (all reproduced, none fixed here)

1. **`BUG_portmap_xor_sigsegv.vhd` -- interpreter SIGSEGV, not an accel bug.**
   A port-map actual that is an expression (`port map (ra => rav xor x"1")`)
   builds an `<inst>.RA_actual` conversion function. After ~2000-5000 evaluations
   the run dies in `ieee_xor_vector_sse41` writing to a null pointer. Measured
   threshold: 2000 iterations clean, 5000 iterations crash. Reproduces with a
   4-bit vector, one instance, no `--accel` involved at all. Every design here
   hoists such expressions into named signals to avoid it.

2. **`NVC_ACCEL_PER_INSTANCE=1` is wrong for parallel chunk topologies.**
   With per-instance chunking, 8 instances of a 5-line registered leaf driven in
   **parallel** give the wrong checksum; the identical leaf **chained** gives the
   right one; and the identical design as one whole-subtree chunk is right in
   both cases. Not caused by shared `.so` (reproduces with 8 distinct `.so`),
   not caused by bit-select port binding (reproduces with named signals).
   `fsm` and `many` are written as chains partly because of this.

Four things fall straight out of the shape contrast, which is what the suite is for.

1. **Operand width is the axis, and it is worth ~9x.** Normalising to instructions
   per design-bit per cycle, `wide` costs ~50-69 and `deep_d128` costs ~5.1;
   Verilator is 0.6-0.9 on both. So we are ~70x off Verilator on wide logic and
   ~8x off on narrow logic, with the same generated-code path, the same bridge and
   the same testbench. `deep_d32` at **6.8x** is the closest anything here gets.

2. **`--accel` is currently a *pessimisation* for 8 of 19 cases.** Every `wide`,
   every `regf` except the largest, and every `act` case runs **fewer** instructions
   in the interpreter (0.24x-0.83x). Only narrow/control (`fsm`), deep-comb (`deep`)
   and fragmented (`many`) designs win. That is not visible without differencing.

3. **Accel does a fixed amount of work per cycle regardless of activity.** `act_lo`
   and `act_hi` are the *same netlist* (`mode` is an input port, not a generic,
   precisely so yosys cannot specialise them). Interpreter cost tracks activity:
   51245 -> 119467 insn/cyc (2.3x) and 118185 -> 323888 (2.7x). Accel does not:
   155564 -> 156129 (**0.4% apart**) and 485570 -> 486232 (**0.1% apart**). In the
   1-of-16 regime accel is 4.1x slower than the interpreter it replaces. The
   event-driven advantage is being thrown away, and there was previously no
   evidence either way.

4. **Compiled cones do scale; chunk count is not the bottleneck.** `deep` accel cost
   is nearly flat in depth (15076 -> 14789 -> 21038 for D=8/32/128) while interp is
   linear (40493 -> 125398 -> 465328). And `many_k24` installs 24 chunks and still
   returns 3.73x, so boundary crossings are not what is costing the wide cases.
